## Project overview

This repo hosts the infrastructure for **GR Cartuchos e Suprimentos de Informática LTDA**'s own operations — the institutional WordPress site (`grcartuchos.com.br`), the company's e-mail, and "GR Sistemas" (an internal PDV/point-of-sale + printer-rental management system, `pdv.grcartuchos.com.br`). None of this is the Zap Agenda/ZapAtende SaaS — that lives in the sibling `zap-agenda` repo. Everything here runs on the *same* VPS as that SaaS purely for infrastructure economy (one server, shared nginx) — see "The seam with zap-agenda" below for exactly how that sharing works.

Origin: all of this used to run on shared HostGator hosting (cPanel account `sistem84`, server `br976.hostgator.com.br`). It was migrated here piece by piece starting 2026-09-07: WordPress site first, then e-mail, then the PDV. Work happened in parallel across two different Claude Code sessions/tools on the same Mac (this one, and a separate "Codex" session) — several services below (phpMyAdmin, the PDV container, code-server, the Python collectors) were built by that other session; read them here rather than assuming you already know the code.

**GR Sistemas is not a multi-tenant SaaS in practice** — despite the login screen literally saying "PAINEL DE CONTROLE SaaS" and the database schema supporting multiple client databases (`sistem84_cliente01`-`07`, `sistem84_grsistemas_parceiro1`), those extra databases are the owner's own old test data, never sold to a real third party. Only `sistem84_impressoras` (the GR Cartuchos business itself) and `sistem84_matriz` (its tenant-registry/auth database) are real and migrated here. Confirmed directly by the business owner — don't assume otherwise from the schema alone.

## The seam with zap-agenda

This repo's `docker-compose.yml` depends on Docker resources that were originally created by the *other* repo's Compose project (back when this content briefly lived inside `zap-agenda/docker-compose.yml` before being split out) — that's why several resources are declared `external: true` with an explicit `zap-agenda_`-prefixed name instead of being created fresh:

- Volumes: `zap-agenda_zap_wp_data`, `zap-agenda_zap_mysql_data`
- Network: `zap-agenda_zap_net`

There is only **one nginx** on the VPS, `zap_nginx`, defined in the `zap-agenda` repo. It reaches this repo's server blocks via a bind mount (`/root/gr-cartuchos-site/nginx:/etc/nginx/sites:ro` on the `zap_nginx` service) plus an `include /etc/nginx/sites/*.conf;` at the end of its own `nginx.conf`'s `http {}` block. This means:
- [nginx/grcartuchos.conf](nginx/grcartuchos.conf) in *this* repo is the actual, only place all of this domain's server blocks live — there's no nginx config duplicated in `zap-agenda`.
- Editing that file takes effect only after `docker exec zap_nginx nginx -s reload` (run from either repo's checkout, it's the same container).
- If this repo isn't checked out at `/root/gr-cartuchos-site` on the VPS, the bind mount silently mounts nothing — no error, the domain just won't resolve to anything. Check the mount before assuming a config bug.
- Renaming this repo's directory on the VPS, or changing the `zap-agenda` Compose project's name, breaks the `external` volume/network references above — don't do either without updating both repos together.

Deploy pattern used throughout this repo's history (no CI/CD yet): edit locally on the Mac → `scp` the changed file(s) to `/root/gr-cartuchos-site/...` on the VPS → `docker compose --env-file .env up -d <service>` and/or `docker exec zap_nginx nginx -s reload` as needed → verify live. Same manual pattern as `zap-agenda`.

## Architecture / services (`docker-compose.yml`)

- **`wordpress`** (container `zap_wordpress`) — the institutional site. Table prefix `wpga_` (not the default `wp_` — the real site's DB dump used this). [wordpress/php-overrides.ini](wordpress/php-overrides.ini) raises PHP's `memory_limit` to 512M — WooCommerce/Elementor exceed the stock 128M on ordinary pages (cart, page editor). The official `wordpress:*-apache` image's generated `wp-config.php` already includes the standard `X-Forwarded-Proto` reverse-proxy HTTPS-detection snippet by default — nothing to add there.
- **`mysql`** (container `zap_mysql`) — shared by WordPress *and* the PDV (`sistem84_impressoras`, `sistem84_matriz`, plus the unused test databases named above). One MySQL server, multiple databases — this is also why `PDV_DB_HOST` and `WORDPRESS_DB_HOST` are both just `mysql`.
- **`phpmyadmin`** (container `gr_phpmyadmin`) — bound to `127.0.0.1:8083` only, never public. Reach it via an SSH tunnel: `ssh -N -L 8083:127.0.0.1:8083 root@82.25.76.130`, then browse `http://127.0.0.1:8083`. Login with `MYSQL_USER`/`MYSQL_PASSWORD` (or root with `MYSQL_ROOT_PASSWORD`) from the VPS's `.env`.
- **`pdv`** (container `gr_pdv`, built from `wordpress/Dockerfile.pdv`) — "GR Sistemas", the legacy PHP PDV/point-of-sale app. Source lives in `pdv/` on disk, **deliberately gitignored** (contains hardcoded legacy credentials and real customer data in some files) — it's copied to the VPS out-of-band, not via `git pull`. DB credentials are injected only via `PDV_DB_USER`/`PDV_DB_PASSWORD` env vars, read in PHP via `getenv()` (see `db_env.php`) — never hardcode a password back into a `.php` file, and never repopulate `empresas.db_pass` in the `matriz` database with a plaintext value.
- **`code-server`** (container `gr_code_server`) — a browser-based VS Code, `127.0.0.1:8085` only, password `CODE_SERVER_PASSWORD`. Mounts are deliberately narrow: `zap_wp_data` (as `site-wordpress/`), `./pdv`, and `./.env` are writable; the Docker socket and any database dump are not mounted, so this editor can't be used to pivot into the host or exfiltrate a full DB dump by itself.
- **`mail`** (container `gr_mail`) — Poste.io, see the "E-mail" section below.

## E-mail (Poste.io)

Chose **Poste.io** over Mailcow specifically because of VPS RAM constraints — Mailcow's own docs recommend ~6GB just for itself, and this VPS only had ~4GB free at migration time. Poste.io is a single container with Postfix+Dovecot+Rspamd+DKIM+Roundcube webmail+an admin panel, workable in ~1-2GB. `DISABLE_CLAMAV=TRUE` in its environment trades away attachment antivirus scanning for RAM headroom — revisit if that becomes a real concern.

`HTTPS=OFF` in its environment is required for this setup: the panel/webmail (port 80 inside the container) is served plain HTTP internally, with `zap_nginx` terminating real TLS in front of it at `https://webmail.grcartuchos.com.br` (its own cert, its own subdomain — deliberately *not* `mail.grcartuchos.com.br`, which is the real MX target). All the actual mail protocol ports (25/465/587/143/993/110/995/4190) are published straight to the VPS's public IP — they're raw TCP, nginx doesn't touch them.

**A container `hostname:` collides with Docker's internal DNS.** The `mail` service sets `hostname: mail.grcartuchos.com.br` so Poste.io self-identifies correctly. Side effect: any *other* container on the same Docker network that resolves that exact hostname (e.g. a one-off `docker run --network zap-agenda_zap_net ...` container doing a migration) gets Docker's internal DNS resolving it straight to the `gr_mail` container's own IP — not the real public DNS answer. This bit an `imapsync` run that tried to use `mail.grcartuchos.com.br` as the *source* (HostGator) host from inside that network: it silently connected to our own new mailbox instead and failed auth confusingly. Fix: use the literal source IP address instead of the hostname when running a one-off container on this network against an external mail server sharing part of that same domain name.

**Mailbox migration** (2026-09-07): used `gilleslamiral/imapsync` in a throwaway container joined to `zap-agenda_zap_net`, migrating `rodolfo@` (2,773 messages) and `janaine@` (10,876 messages) from HostGator's Dovecot straight into Poste.io, `--syncinternaldates` to preserve real arrival dates. Ran it a second time right before the DNS/MX cutover as a final catch-up pass (came back with 0 new messages both times — nothing arrived in the gap). If this is ever needed again for a mailbox not yet migrated, the same two-pass pattern (migrate once, migrate again immediately before cutover) is the way to bound data loss to whatever arrives in the last few minutes.

**Retention cleanup** (2026-09-07): after migrating, the owner decided to keep only the last 2 years on this server (older mail stays retrievable from HostGator until that account is ever cancelled — the migration was a copy, not a move, so nothing was lost by trimming the new copy). Used Dovecot's own `doveadm` (bundled in the Poste.io image, no separate install needed) rather than IMAP client-side deletion: `doveadm search -u <user>@grcartuchos.com.br mailbox '*' before 2024-09-01` to count/preview first (dry run — `search` only lists, doesn't delete), then `doveadm expunge -u <user>@grcartuchos.com.br mailbox '*' before 2024-09-01` to actually delete once the count was confirmed with the owner. `mailbox '*'` matters — without it the search/expunge only covers INBOX, missing Sent/Archives/etc., which is most of the volume in an old mailbox. Result: `janaine@` 10,876 → 3,258 messages, `rodolfo@` 2,773 → 670. `sac@atendezapbrasil.com.br` was deliberately left untouched (only 286 messages total, all recent — no old backlog to trim).

**DKIM**: Poste.io generates its own key with its own selector name (not `default` — e.g. `s20260907624`), so it coexists with the old HostGator DKIM key at `default._domainkey` without conflict until cutover, at which point the old one becomes unused and can be deleted. **This got missed once for real** — the DKIM TXT record was forgotten during the initial DNS-provider switch (see below) and the gap wasn't caught until a deliberate `dig TXT default._domainkey...`/`s2026...` check after the fact. DKIM is easy to forget on any future DNS cutover because it doesn't show up as an A/MX/CNAME — it's invisible until an actual signed message gets checked. Always explicitly verify both the old and new DKIM selectors with `dig` immediately after any DNS provider change for a domain that sends mail.

**Port 25 "blocked" was a false alarm caused by testing from the wrong network.** `nc -zv <vps-ip> 25` timed out consistently when run from the Mac doing this migration, while 587/993 succeeded — the textbook signature of an ISP/network blocking outbound port 25 client-side (extremely common, unrelated to the destination). Hostinger support first suggested it was their managed VPS firewall (it wasn't — creating and activating a fully-populated firewall rule set including port 25 changed nothing) and then correctly pointed out port 25 isn't blocked by default on their VPS plans, suggesting the timeout might be network-path-specific. Confirmed independently via MXToolbox's SMTP diagnostic tool (`smtp:<ip>` in their SuperTool) — which connects from *their* servers, not the tester's — got a clean `220 ... ESMTP Haraka/3.0.3 ready` banner. **Lesson: before escalating a port-connectivity "it's blocked" finding to a hosting provider, verify from an independent third-party network path (MXToolbox's SuperTool, or similar), since testing from your own machine only proves what your own network allows outbound, not what's reachable from the internet at large.**

If a Hostinger-managed VPS firewall is ever actually needed for this VM: creating one and activating it makes it **default-deny everything not explicitly listed** — the create-rule tool's own docs say this. Before activating, enumerate every currently-listening public port on the VPS (`ss -tlnp | grep LISTEN`, excluding anything bound to `127.0.0.1`) and add an accept rule for each one, SSH (22) included, or you will lock yourself out / take down the site and API. This was done once as a (ultimately unnecessary, since it didn't fix the port 25 non-issue above) test and then deliberately deactivated again afterward, specifically to avoid the ongoing maintenance burden of remembering to add a firewall rule every time a new container publishes a new port.

**DNS cutover** (2026-09-07): the domain's nameservers were on Cloudflare with no known login to that account. Two alternatives were considered and rejected in favor of a third: (1) recovering Cloudflare access — never pursued; (2) moving DNS to Hostinger — blocked, their DNS zone API returns `404 Domain not found` for any domain not already present in that Hostinger account's portfolio, and adding an externally-registered domain there isn't available via API, only hPanel, and even then wasn't attempted since (3) turned out simpler: **switch the domain's nameservers back to Registro.br's own** (`d.sec.dns.br`/`f.sec.dns.br` for this domain) — Registro.br provides its own free DNS zone editor for any domain registered there, no third-party account needed at all. Before switching, the *existing* Cloudflare-era DNS zone was inventoried via plain public `dig` queries (A/MX/TXT/CNAME — no login needed, DNS records are public) so nothing (especially mail-related SPF/DKIM/MX) got lost in the move. `mail.grcartuchos.com.br`'s A record was the actual MX cutover trigger — changed last, only after the mailbox migration and DKIM were both already in place and tested.

### `atendezapbrasil.com.br` (the Zap Agenda/ZapAtende SaaS) shares this same Poste.io instance (2026-09-07)

Rather than standing up a second mail server, the SaaS domain's e-mail was migrated into the *same* `gr_mail` container as a second virtual domain — Poste.io supports multiple domains natively (Virtual domains list in its admin panel). This domain used to run on Hostinger's own hosted e-mail (`mx1/mx2.hostinger.com`), with one real mailbox, `sac@atendezapbrasil.com.br`, that the `zap-agenda` backend itself also uses to *send* transactional e-mail (registration, password reset) via SMTP — see `backend/src/services/email.ts` and `SMTP_HOST`/`SMTP_USER`/`SMTP_PASSWORD` in `zap-agenda`'s `.env`. Migrating this domain's mail therefore has two parts, not one: the mailbox itself, *and* the backend's outbound SMTP credentials — forgetting the second half leaves the app unable to send any transactional e-mail even though the mailbox migration itself succeeds.

Sequence used: create the domain + a fresh DKIM key in the existing Poste.io panel → create `sac@atendezapbrasil.com.br` there → `imapsync` the mailbox from `imap.hostinger.com` (286 messages, 0 errors) → change `atendezapbrasil.com.br`'s MX and SPF via the **Hostinger DNS zone API** (this domain *is* in the Hostinger account's portfolio, unlike `grcartuchos.com.br` — no Registro.br-style workaround needed here, the API just works) → update `zap-agenda`'s `.env` (`SMTP_HOST=mail.grcartuchos.com.br`, `SMTP_PORT=587`, `SMTP_PASSWORD=<the new Poste.io mailbox password>`) → `docker compose up -d --force-recreate zap_api` → one more `imapsync` catch-up pass (0 new messages, as expected — only minutes had passed).

Two Hostinger DNS API gotchas hit during this:
- **`MX` records need the priority embedded in the `content` string** (e.g. `"1 mail.grcartuchos.com.br."`), not as a separate `priority` field — passing a separate `priority` field alongside `content` silently causes a `500 [DNS:1000] Server Error` on every attempt, with no indication of what's structurally wrong. Match the format `dig` itself would show for that record type.
- **A successful `200 {"message":"Request accepted"}` response doesn't mean the authoritative nameservers have the new value yet** — there's a real (tens-of-seconds-plus) gap between the API accepting a change and it actually being served. Confirmed once by reading the zone straight back from the same API (`GET .../zones/{domain}`, which showed the *new* value immediately) while `dig ... @ns1.dns-parking.com` (this domain's actual authoritative server) still returned the *old* one for another ~20+ seconds. Don't conclude a Hostinger DNS change failed just because a `dig` right after the `200` still shows the old value — re-check the API's own zone read first, then wait and re-`dig`.
- Also re-confirmed: `overwrite: true` on this API scopes to the specific `name`+`type` pair sent in that request, not the whole zone — changing just the `_dmarc` TXT record (see below) with `overwrite: true` left every other record (MX, A, the unrelated SPF/other TXT records) untouched. Verified explicitly after the fact rather than assumed, given how destructive being wrong about this would be.
- A `_dmarc` TXT added with `overwrite: false` (merge mode) on a name that *already had* an existing record produced **two DMARC TXT records on the same name** — invalid per the DMARC spec (exactly one is expected; validators' behavior with two is inconsistent/undefined). Re-adding the same record with `overwrite: true` correctly replaced both with just the one intended. Before adding a DMARC (or any single-value-expected) TXT record with the merge-mode default, check whether one already exists first.

DMARC was added for **both** domains this same day, `p=none` (monitor-only, `rua=mailto:rodolfo@grcartuchos.com.br`) — deliberately not `quarantine`/`reject` yet, to avoid silently dropping legitimate mail before anyone's looked at a single report. Revisit once reports have been reviewed for a while.

### Poste.io was serving its own self-signed cert on the mail ports — broke phone mail apps (2026-09-08)

**Symptom**: `janaine@grcartuchos.com.br` stopped syncing on her phone's mail app, while webmail (`webmail.grcartuchos.com.br`, browser) kept working fine. That asymmetry is the tell — webmail goes through `zap_nginx`'s HTTPS (a real Let's Encrypt cert), but a phone's native mail app connects *directly* to `gr_mail`'s raw IMAP/SMTP ports (993/587/etc.), which never touch nginx at all.

**Root cause, confirmed with `openssl s_client -connect mail.grcartuchos.com.br:993`**: Poste.io was presenting its own bundled factory self-signed certificate (`O=Poste.io`, issued 2020, valid to 2030 — a fixed default baked into the image, not something generated fresh) instead of a real one. This makes sense in hindsight: `HTTPS=OFF` was set so `zap_nginx` could terminate TLS for the webmail path, but that means Poste.io's *own* internal Let's Encrypt automation (which needs port 80 to itself for its ACME challenge) can never succeed here, since nginx already owns port 80/443 for the domain. So Poste.io silently fell back to its shipped self-signed default for every protocol *except* the one nginx fronts — and had presumably been doing so since the mailbox migration, meaning this may have been broken from day one rather than a new regression (unclear exactly when the phone stopped syncing vs. when this was first noticed).

**Fix applied**: Poste.io reads its TLS material from three fixed files inside its data volume — `/data/ssl/server.crt`, `/data/ssl/ca.crt`, `/data/ssl/server.key` (see `/data/ssl/README.md` inside the container for the exact expected format — one cert per file, no combined `fullchain.pem`). Since `mail.grcartuchos.com.br` (the real MX target, DNS already pointed at this VPS) had no cert of its own yet, distinct from `webmail.grcartuchos.com.br`'s:
1. Added an HTTP-only nginx block for `mail.grcartuchos.com.br` in [nginx/grcartuchos.conf](nginx/grcartuchos.conf) (ACME challenge + redirect to webmail) — needed so certbot's webroot method could validate the domain, even though nothing browses to it directly.
2. Issued the cert: `docker run --rm -v zap-agenda_certbot_conf:/etc/letsencrypt -v zap-agenda_certbot_www:/var/www/certbot certbot/certbot certonly --webroot -w /var/www/certbot -d mail.grcartuchos.com.br --key-type ecdsa`.
3. Copied `cert.pem`→`server.crt`, `chain.pem`→`ca.crt`, `privkey.pem`→`server.key` into the `gr_mail_data` volume's `/data/ssl/`, `chown mail:mail` (uid 8 inside the container — confirmed via `docker exec gr_mail id mail`), then `docker restart gr_mail`.
4. Verified with `openssl s_client` against both port 993 and 587 (STARTTLS) — both now present the real `Let's Encrypt` cert for `mail.grcartuchos.com.br`, not the Poste.io default.

**A separate, more general gap this surfaced: there was no certificate renewal automation at all on this VPS** — `crontab -l` on the VPS came back completely empty, for any domain, not just this one. Every cert issued throughout this project's history (WordPress, PDV, phpMyAdmin/code-server, webmail, api, now mail) would have silently expired ~90 days after issuance with nothing renewing them. Originally fixed with an ad-hoc `/root/renew-certs.sh` script + a raw user-crontab entry, deliberately *not* version-controlled at the time.

**Collision found and resolved (2026-09-08): a second, independent fix for the exact same gap already existed, version-controlled, from the Codex session working in parallel on this same repo** — [ops/renew-certificates.sh](ops/renew-certificates.sh) + [ops/gr-certbot-renew.cron](ops/gr-certbot-renew.cron), installed on the VPS as `/etc/cron.d/gr-certbot-renew`, running `certbot renew` once daily at the same `17 3 * * *` slot. **Both crons were live on the VPS simultaneously** — two unrelated `certbot renew` invocations racing against the same `zap-agenda_certbot_conf` volume at 3:17am. Resolved by merging: kept Codex's version-controlled script as the single source of truth (proper practice — this ad-hoc one never should have lived VPS-only in the first place), added the `mail.grcartuchos.com.br`-specific Poste.io cert-propagation logic (the `md5sum`-gated copy-into-`/data/ssl/`-and-restart-`gr_mail` step described above) into it, bumped its schedule to twice daily (`17 3,15 * * *`) to match certbot's recommended cadence, redeployed, and **deleted the ad-hoc `/root/renew-certs.sh` and its separate user-crontab entry entirely**. The script now does: `certbot renew` against the shared `zap-agenda_certbot_conf`/`zap-agenda_certbot_www` volumes → `docker exec zap_nginx nginx -s reload` (covers every nginx-fronted domain, safe to run even when nothing renewed) → *only if* `mail.grcartuchos.com.br`'s `cert.pem` actually changed, re-copy into Poste.io's `/data/ssl/` and `docker restart gr_mail` (gated so the mail server isn't restarted daily, only on the ~1-in-90-days it actually renews). Logs to `/var/log/gr-certbot-renew.log` on the VPS. **Lesson for whoever works in this repo next, alongside another AI session:** check `crontab -l` *and* `/etc/cron.d/` on the VPS (not just one) before assuming a cron doesn't exist yet — a parallel session may have already built it.

**If this ever needs to be redone for a new/renamed mail hostname**: the three-file split (`server.crt`/`ca.crt`/`server.key`, not a single `fullchain.pem`) is Poste.io-specific — don't assume it matches nginx's `ssl_certificate`/`ssl_certificate_key` two-file convention used everywhere else in this repo's nginx config.

## Site-wide SEO/GEO content audit — 113 doorway pages found (2026-09-08)

**The single highest-priority SEO finding on this site.** Pulled every published page's title, Yoast SEO title/meta-description, and content length in one pass (`wp eval-file` with `$wpdb`/`get_post_meta` — `wp db query` doesn't work in this container, the `mysql` CLI binary isn't installed, only PHP's mysqli extension). Of 154 published pages, 113 are "locação de impressoras [bairro/cidade]" pages, one per neighborhood across São Paulo/Guarulhos. **Directly compared the full body text of two of them (São Lucas vs. Pirituba, both exactly 18,770 content-length characters) — word-for-word identical except the neighborhood name.** This is a textbook doorway-pages pattern (Google's Spam Policies explicitly define and penalize this: "multiple pages... with substantially similar content... optimized for specific, similar search queries"), and a real risk to the *entire* site's rankings, not just these pages — plus it's close to worthless for GEO, since there's nothing neighborhood-specific for an AI engine to cite one page over another.

**Confirmed cleanup, done**: trashed (not permanently deleted — recoverable) 4 zero-value pages found during the same audit — the already-known broken `template-conectar.php`/"Conectar WhatsApp" orphan (post 4347/4359), a live "página de testes" with empty content (4061), and two published pages with no title and no content at all, reachable at `/4704-2/` and `/4703-2/` (4704/4703) — pure index bloat with no discoverable purpose.

**Secondary, lower-priority finding**: 150 of 154 pages have no custom Yoast SEO title/meta-description (relying on Yoast's default template pattern, e.g. `%%title%% %%page%% %%sep%% %%sitename%%`) — not literally duplicated across pages since `%%title%%` includes each page's own unique title, but a missed CTR-optimization opportunity worth doing *together with* the doorway-page rewrite below (writing a real per-neighborhood meta description makes little sense while the underlying page content is still a template clone).

**Chosen direction (owner's explicit decision, 2026-09-08): rewrite the 113 pages with genuinely unique content, gradually, in batches (~10-15 pages at a time)** — explicitly *not* the alternative that was offered (consolidating into fewer, stronger regional hub pages instead of keeping 113 thin ones). Real differentiators the owner gave directly, now the backbone of every rewrite: **24-business-hour on-site technical dispatch** and **same-day supply delivery by motoboy**, both gated behind a genuinely distinctive **in-house remote IT support desk** that triages every call first (remote access to diagnose printers/scanners) before deciding whether to dispatch a technician or just courier a toner — a real operational detail worth repeating across pages (it's not filler, it's an actual differentiator competitors likely don't communicate), combined with genuine per-page variation: approximate distance in km from the Guarulhos HQ (Av. José Miguel Ackel, 2047), the SP zone, and named neighboring districts. Distances used so far are the model's own reasonable estimates (not measured via a mapping API) — treat them as approximate, framed with "cerca de" in the copy, not as verified figures.

**Batch 1 — done, 2026-09-08: 9 of 113 pages rewritten.** São Lucas (3254), Pirituba (3023), Itaquera (2926), Ipiranga (2847), Santana (2531), Tucuruvi (2571), Tatuapé (1775), Mooca (2594), Vila Guilherme (3130). ### Real incident: editing `_elementor_data` via WP-CLI/`wp eval` broke the live homepage, twice, before being fixed

Attempting to remove the two duplicate widgets by editing post 2's `_elementor_data` postmeta directly (dump via `wp post meta get`, edit the JSON in Python, write back via `wp eval '...update_post_meta(2, "_elementor_data", file_get_contents(...))...'`) went wrong in **two distinct, separate ways**, each initially misdiagnosed:

1. **`update_post_meta()` calls `wp_unslash()` internally**, assuming its input carries PHP magic-quotes-style extra backslashes that need stripping. A raw JSON string read via `file_get_contents()` doesn't have those — so `wp_unslash()` incorrectly stripped real, structurally-necessary backslashes (like escaped quotes) out of the JSON, corrupting it (confirmed by writing it back and getting a `json.loads()` parse error). **Fix: wrap the value in `wp_slash()` before passing it to `update_post_meta()`** — `update_post_meta(2, '_elementor_data', wp_slash($json))` — so the unslash cancels out and the original string survives intact.
2. **Even with valid JSON restored, one specific widget (the homepage Hero, id `304f147` — real visible content, never intended to be touched) started rendering its raw HTML/comments/JSON-LD as literal visible page text** (`<!--` showing up as `&lt;!--` in the actual browser DOM — confirmed via `document.body.innerText.includes(...)` returning `true`, and via `document.documentElement.outerHTML` showing no comment markers at all around that text). Root cause: **`wp eval` runs without an authenticated admin user context by default, and something in the save path (Elementor and/or WordPress's KSES HTML-sanitization) escapes raw HTML for users lacking `unfiltered_html`.** A real logged-in admin has that capability; a bare `wp eval --allow-root` invocation doesn't carry it. **Fix: pass `--user=1`** (or whichever user ID is an actual Administrator) to `wp eval`, so the save path sees a user with `unfiltered_html` and doesn't escape anything.
3. A secondary complication while diagnosing (2): the escaping was invisible to plain `curl` checks (with or without a real Chrome User-Agent) — curl kept showing correctly-unescaped HTML even while a real, fresh, `--headed` Chrome browser rendered the escaped/broken version for the same URL at the same time. Never fully explained (WP Rocket page-cache serving a stale variant to real browsers but not curl is the leading theory, given this site's heavy WP Rocket/Elementor CSS-delivery caching — see the two now-superseded, unnecessary detours below), but **the practical lesson is: verify a suspected content bug with a real, headed browser screenshot, not `curl`** — they can genuinely disagree here.

**Both were fixed in the end (`wp_slash()` + `--user=1` together), but two other things were tried and unwound as unnecessary detours** before the real fix was found — worth knowing so they're not repeated: disabling WP Rocket's `remove_unused_css`/`optimize_css_delivery`/etc. settings (had nothing to do with it; re-enabled afterward), and a full page-cache directory wipe (`wp-content/cache/wp-rocket/*`, `used-css/*`, `critical-css/*` — harmless and worth doing after any content fix regardless, but wasn't the actual fix either time).

**What actually, finally resolved the live incident**: logged into `wp-admin` for real (the one existing admin, `Davi1023@`, previously had no password on record here — the user supplied one directly) — with `--user=1` already fixing the underlying data, this step turned out to matter less for correctness and more for *closing the loop cleanly*: opening the Elementor editor (`wp-admin/post.php?post=2&action=elementor`) rendered the (already-fixed) content correctly, and clicking **Publicar** (after forcing Elementor's dirty-flag with `elementor.saver.setFlagEditorChange(true)` via `eval` — the button is disabled until something's "changed") triggered a full, properly-authenticated resave that flushed every remaining cache layer at once. Verified fixed with a completely fresh, cache-less browser session afterward.

**Takeaway for next time this repo's Elementor content needs a programmatic edit**: use `wp_slash()` + `--user=<a real admin ID>` from the start, and treat "open the Elementor editor and click Publish" (forcing the dirty flag via `eval` if nothing visibly changed) as the standard *last step* of any raw postmeta edit to this data — not just a recovery move. Better yet, for content or structural changes to a *live* page, prefer driving the actual Elementor editor UI throughout rather than raw JSON manipulation at all — see the "Automation note" pattern established for `zap-agenda`'s `agent-browser` usage (`--headed --executable-path "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --profile <fresh isolated dir>`, since the bundled Chrome-for-Testing binary doesn't run on this Mac's OS).

## Panels exposed via their own subdomains (2026-09-07)

`phpmyadmin.grcartuchos.com.br` (→ `phpmyadmin:80`) and `editor.grcartuchos.com.br` (→ `code-server:8080`) were added as public HTTPS subdomains, same pattern as everything else in this repo — previously these two services were only reachable via an SSH tunnel to their `127.0.0.1`-bound host ports. Both share one Let's Encrypt certificate (issued with `-d phpmyadmin.grcartuchos.com.br -d editor.grcartuchos.com.br` in one `certonly` call — a single cert with two SAN names, so both server blocks' `ssl_certificate` line points at the `phpmyadmin.grcartuchos.com.br` cert directory, not two separate directories).

**phpMyAdmin gets a second auth layer** (`auth_basic` in nginx, backed by `nginx/htpasswd_pma` — gitignored, VPS-only, generated with `openssl passwd -apr1` since `htpasswd` itself isn't installed on this VPS) on top of its own database login, because it exposes real customer data (names, CPF/CNPJ, phone numbers) to the public internet otherwise protected only by a single password — phpMyAdmin installs are a common bot-scanning target. `editor.grcartuchos.com.br` (code-server) needs `proxy_set_header Upgrade`/`Connection "upgrade"` in its nginx block for its WebSocket-based editor connection to work — a plain reverse proxy block without those breaks it silently (loads the login page fine, breaks after auth).

**`htpasswd_pma` must not be `chmod 600`.** It was created with `600` right after `scp`-ing it to the VPS (reasonable instinct — it holds a password hash), which broke every request to `phpmyadmin.grcartuchos.com.br` with a bare-nginx `500` (not a phpMyAdmin/PHP error page — nginx itself failing before ever reaching the upstream). `docker logs zap_nginx` showed the real cause immediately: `open() "/etc/nginx/sites/htpasswd_pma" failed (13: Permission denied)` — the nginx worker process inside the container runs as a different, unprivileged user than the `root` that owns the file on the host, so `600` (owner-only) leaves it completely unreadable to nginx. Fixed with `chmod 644` (world-readable is fine here — the file holds a bcrypt/apr1 *hash*, not the plaintext password, and it's not otherwise reachable outside the container filesystem anyway). General lesson: **when a public URL for something proxied by this shared nginx returns a 500 with nginx's own default error page** (not the backend app's error page), check `docker logs zap_nginx` first — it's almost always a file it can't reach (permissions, or a missing bind-mounted path), and the message names the exact file.

## PDV / GR Sistemas migration (2026-09-07, in progress)

The PDV runs live business operations (real sales, real customer records, real printer-counter billing data) — treat any of its data very differently from the WordPress site's: a stale WordPress page is invisible to users; a stale PDV database, table row, or a `DROP DATABASE` run against the wrong host is a real operational incident.

**Printer counters update continuously, independent of the store's own hours.** The `contador` table in `sistem84_impressoras` receives a row-per-client-printer, with an `UPDATE` fired whenever that client's own computer (running a background collector script) boots up and reports in — this has nothing to do with whether the GR Cartuchos *store itself* is open. Confirmed live during migration: on a day the physical store was closed for a holiday, several `contador` rows still updated at 13:39, 16:35, 16:37, and 16:40 — apparently a handful of client machines were switched on anyway. **Never assume "the store's closed today" means the PDV's data is frozen** — verify actual freshness (e.g. `SELECT id, cliente, data FROM contador WHERE id IN (...)` against a handful of known rows, compared with a fresh pull from the source) before trusting a database copy taken earlier in the day.

**A full-database `mysqldump`-then-import "refresh" is the wrong tool for a single already-populated table.** The first refresh attempt tried piping a full phpMyAdmin export back into the already-imported `sistem84_impressoras`/`sistem84_matriz` databases — every `CREATE TABLE` failed with `Table already exists` (phpMyAdmin's default export has no `DROP TABLE IF EXISTS`), and the `mysql` CLI's default behavior of continuing past errors let subsequent `INSERT`s silently target the pre-existing (stale) tables instead of failing loudly, meaning the "refresh" looked successful but changed nothing. The fix used was scoped exactly to the one table that actually has time-sensitive data (`contador`): `TRUNCATE TABLE contador;` on the destination, then extract just that table's `INSERT` statement out of the fresh phpMyAdmin dump (find its start/end lines with `grep`/`awk` for `INSERT INTO \`contador\`` through the line ending in `);` rather than `),`), and import only that fragment. Don't reach for "drop and recreate the whole database" as a first move for a data-freshness problem — scope the fix to the specific table(s) that actually change.

**MySQL 8 (this VPS) rejects zero-dates that HostGator's older MySQL/MariaDB accepted.** Importing the `contador` table's fresh data failed outright with `Incorrect datetime value: '0000-00-00 00:00:00.00'`, and — because this was one single multi-row `INSERT ... VALUES (...),(...),(...);` statement — the *entire* insert was rejected atomically, leaving the table completely empty (worse than before the `TRUNCATE`). Fixed by running that one import with strict mode relaxed for the session only: `mysql --init-command="SET sql_mode=''" ...`, not by editing the dump file or changing the server's global `sql_mode`. If any other table from the legacy HostGator database ever needs a similar refresh, expect the same class of error for any zero-date/zero-datetime column and use the same one-off `--init-command` fix rather than a permanent server-wide setting change.

**Remote MySQL access to HostGator was already open to any IP** (cPanel → "Remote Database Access" already had a `%` wildcard host entry) — worth checking first before assuming a password reset or a new access grant is needed to pull data directly. phpMyAdmin's UI navigation (via `agent-browser`) turned out slower/more fragile than expected for this task (several dead-end clicks landing on the wrong page) — for a scripted single-table export, direct `mysql`/`mysqldump` over the already-open remote access would have been faster than driving phpMyAdmin's export form through a real browser, if credentials for a suitable DB user are known.

**`sistemasrjd.com.br` (a separate, distinct domain, also on the same HostGator account/IP, own DNS at `ns976`/`ns977.hostgator.com.br`) is what the *already-deployed* Python collector scripts on client machines actually report to today** — not `pdv.grcartuchos.com.br` and not `api.grcartuchos.com.br`. It's legacy branding from before "GR Cartuchos"/this migration. **Cutting over `pdv.grcartuchos.com.br`'s DNS does not affect this at all** — they're unrelated domains, so counters keep landing only on HostGator's original database through `sistemasrjd.com.br` regardless of anything done to `grcartuchos.com.br`'s zone. A rewritten collector already exists in this repo ([collectors/coletor_multimodelo_api.py](collectors/coletor_multimodelo_api.py), with matching Windows/macOS build scripts and compiled artifacts under `collectors/dist/`) that correctly targets `https://api.grcartuchos.com.br/contador` (already live, proxied by `zap_nginx` straight to `gr_pdv`'s `api/contador.php`) — but it still needs to be installed on each client machine, replacing the old script, before that client's counters start landing on the new server.
